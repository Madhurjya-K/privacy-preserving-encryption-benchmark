# Threat model, leakage and adversarial diagnostics

Owner is trusted and controls classification, independent AES/chaos/HMAC keys and Paillier private key. Hybrid worker functions receive ciphertext rows and public modulus only. Local Spark driver nevertheless holds all keys and owner plaintext within the same machine; this is not isolation against a root attacker. AES baseline workers intentionally receive an AES key and plaintext. A semi-honest cloud can inspect worker inputs/outputs. Stored-data tampering is checked separately from compute correctness.

Leakage: grouping keys, IDs, row/partition/group sizes, null locations, ciphertext lengths, query/access patterns and authenticated per-field absolute bounds. Bounds are derived from plaintext and revealed; if this leakage is unacceptable, replace maxima with independently chosen public conservative limits and test their validity. No differential privacy, output thresholding, oblivious grouping, hidden predicates or verifiable computation is provided. Tiny/overlapping groups can leak individuals via results.

Paillier security rests on its standard assumption and fresh randomness, not this handwritten implementation being audited. Miller-Rabin uses 64 random rounds, probabilistic rather than certified primes. Python big-integer operations are not constant-time. Numeric values must stay inside the strict n/3 signed range; bound check is essential because modulo-n wrap can yield valid-looking decoded values. Private key material never persists in reports. Input/source checksum hashes are not proof of source authenticity.

AES-GCM requires nonce uniqueness per key. RecordCipher rejects explicit repeat nonces in that object and hybrid protect creates one object per bundle. New bundles have fresh random nonces; there is no durable cross-run nonce registry. Random 96-bit collisions are negligible at tested scale but uniqueness across long-running retries/restarts is not guaranteed operationally; production should persist a per-key allocation strategy or rotate keys. Chaos nonce collision checking is per protection call, with the same limitation. AAD is UTF-8 record ID, scoped to a bundle through the manifest/keys; IDs alone are not globally unique.

Manifest uses deterministic UTF-8 sorted-key JSON with no NaN, then canonical sort of complete record byte strings within each partition. Sorting deliberately ignores within-partition order. Index and counts are authenticated: deletion, insertion, duplication, bit flip, cross-partition movement/swap, nonce/Paillier ciphertext change, metadata tamper, digest replacement without HMAC, wrong owner and old version are negative-test classes. A positive test verifies reorder within the same partition still passes. The trusted current version is a caller-supplied owner fact, not inferred from the possibly stale manifest. Library query/materialize functions do not automatically verify, allowing timing separation; callers MUST verify first. The benchmark does so. A malicious cloud may still return an aggregate for a different set, and no stored-data manifest detects that.

H-CHAOS is not authenticated by itself and has a 64-bit finite state. Protected storage integrity depends on the keyed manifest. Diagnostics in security.py execute key/nonce bit sensitivity, full-state repeats over bounded trajectory lengths, a deliberate nonce-reuse XOR demonstration, and a restricted partial-state enumeration. The latter grants rq and the high 52 state bits, enumerates 4096 low-bit candidates, matches eight known keystream bytes and predicts eight held-out bytes. This privileged search is not a realistic unrestricted attack nor evidence that full-state/key recovery is infeasible. It explicitly documents the restricted search space and prior knowledge. Statistical sensitivity and no short cycle in a limited scan do not prove pseudorandomness or confidentiality.

External complete NIST SP 800-22 evaluation is pending. No homegrown diagnostic is labeled NIST. NIST test success itself would not prove security. Retain AES-GCM as the standard comparator; do not deploy H-CHAOS based on apparent random-looking output.

exposure_audit examines only serialized protected JSON for supplied literal canaries. It does not scan JVM memory, Spark logs, disk spill, OS swap, network traces or crash dumps. Negative findings are bounded observations, not proof of no exposure. Numeric string matches can occur accidentally inside decimal ciphertexts. Evidence of leakage is a finding; absence is not a security theorem.

Observed initial restricted search: 4096/4096 candidates matched both tested prefix and held-out bytes; unique state recovery did not occur. Do not summarize this as a successful full-state recovery.
